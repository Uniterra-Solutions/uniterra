# Module: uniterra-desktop

**Purpose:** Electron shell over the bundled DeepSeek Harness (dsh) CLI — supervises the dsh web server child and hosts its Web UI in a BrowserWindow. Uniterra IS the dsh desktop surface: it runs the bundled dsh against the user's normal dsh configuration; no app-owned home, no seeding, no profile scaffolding.

Source: `packages/uniterra-desktop/src/` (`main.ts`, `dsh-process.ts`, `dsh-cli-path.ts`, `builtin.ts`, `preset-compat.ts`, `notifications.ts`, `turn-observer.ts`, `dsh-observer.ts`); packaging `electron-builder.yml`; tests `test/*.mjs`.

## Public API

`src/dsh-process.ts`:

| Symbol              | Signature                                                                 | Description                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DshRuntimeOptions` | `{ cli, nodeExec, dshHome?, dshBundledSkillDir?, profile, port?, args? }` | Spawn options                                                                                                                                                                                     |
| `DshRuntimeHandle`  | `{ url, child, exited: Promise<number \| null> }`                         | Live runtime handle                                                                                                                                                                               |
| `awaitReadiness`    | `(stdout: Readable, timeoutMs = 60_000) => Promise<string>`               | Resolve first `http://127.0.0.1:<port>` URL on stdout; on timeout, SIGTERM child and reject with last 4000 chars of stderr                                                                        |
| `startDsh`          | `(options: DshRuntimeOptions) => Promise<DshRuntimeHandle>`               | Spawn `node <cli> --profile <profile> --no-open` with `DSH_HOME`, `DSH_BUNDLED_SKILL_DIR`, `ELECTRON_RUN_AS_NODE=1`, `NO_COLOR=1`; await readiness, rethrowing at once when the child exits first |
| `stopDsh`           | `(child: ChildProcess, timeoutMs = 10_000) => Promise<void>`              | SIGTERM, race exit vs timeout, SIGKILL if still alive                                                                                                                                             |

`src/builtin.ts` — see [vendor-plugins.md](vendor-plugins.md) for the exact built-in lists and provisioning semantics; exports: `registerBuiltinPlugin` (declarative registry of `NpmBuiltin` / `CopyBuiltin` / `RetiredBuiltin` entries), `builtinPlugins`, `npmBuiltinSpecs`, `copyBuiltins`, `retiredBuiltinNames`, `builtinPackageName`, `expectedBuiltinBundles`, `hasAllBuiltins`, `copyBuiltinsStale` (unified vendored/workspace staleness), `removeRetiredBuiltins`, `ensureBuiltinPlugins`, `ensureWorkflowCapsules` (provisions the `review` capsule into `$DSH_HOME/workflows` and removes the retired capsules), `RETIRED_WORKFLOW_CAPSULES`, `builtinSkillsDir` (exported but unused — `main.ts` uses its own `skillsDir()`).

`src/preset-compat.ts` — agent-preset compatibility row for the 0.1.2-rc.1 `code` (Code Mode) → `ptc` rename, **converged on dsh 0.1.5-rc.2: only the settings half still needs it.** Session HEADERS are migrated natively — the installed chain `[sessionFormatV0ToV1, sessionFormatV1ToV2, sessionFormatV2ToV3]` (`vendor/dsh-harness/packages/session/session-format-catalog/src/generated.ts:18`; current version 3 at `packages/core/session/src/types.ts:88`) rewrites `agentPreset: "code"` to `ptc` in every v0/v1/v2 header and in every `agent-preset/selected` event (`packages/session/session-format-v2-to-v3/src/migration.ts:16-18,140-144`), and deliberately leaves a native v3 header alone — so resume of an old session no longer needs the row. The settings row `agent-presets.default: code` is NOT migrated: `vendor/dsh-harness/packages/settings/` ships no migration, and the roster reads the row verbatim as its default preset id (`packages/preset/agent-presets/src/index.ts:240-242`, `this.settings?.get().default ?? this.config.default`), so a session that names no preset still fails with `agent-presets: preset "code" not found (available: standard, ptc, minimal, cordis)`. `ensureAgentPresetCompatibility(dshHome, sourceRoot)` provisions a user preset `code` (byte copy of the shipped `ptc` composition) into `$DSH_HOME/.agent-presets/`; it never overwrites an existing file (a user-authored preset is preserved) and is idempotent. **Removal condition:** delete the module when the stored `agent-presets.default` no longer names `code` AND no session header or `agent-preset/selected` event still records it (a v3 session written while the default pointed at this row keeps `code`, which the migration does not touch).

`src/notifications.ts` — the feature's decided half (no I/O, no Electron, no timers): `turnNotification(input)` maps one `turn/end` frame to a `{ title, body }` payload or `undefined`; `createTurnDeduper()` gives the replay guard (`shouldNotify(sessionId, turn)` is true exactly once per distinct pair — a follow stream replays its opening window on every reconnect, so the same finished turn arrives more than once by design); `readTurnNotificationsEnabled` / `writeTurnNotificationsEnabled` own the `notifications.turnComplete` key in the profile's `.uniterra.json` — the SAME file `builtin.ts` owns for the optional-plugin toggle, so writes stay additive (every other key survives) and an illegible user file is never rewritten.

`src/turn-observer.ts` — `observeTurns(deps)`, the semantics half: session discovery and the per-session frame stream are injected (`listSessions` / `followSession`), so the selection rule, notice payload, dedupe, live toggle and fail-soft guarantees are decidable with a fake. Only user-facing sessions are followed at all (`origin === 'subagent'` is skipped), the enabled state is consulted PER EVENT so the menu checkbox takes effect without a restart, and `observeTurns` never rejects and never stops at the first failure.

`src/dsh-observer.ts` — `startDshTurnObserver(options)` returns a `DshTurnObserverHandle` (`stop()`) SYNCHRONOUSLY and runs detached. Wire facts verified read-only against `vendor/dsh-harness`: the readiness token is accepted only on `GET /`, where it mints the authority-bound `dsh-auth-<hash>` cookie, and every `/api` call AND the WebSocket upgrade must carry that cookie (`packages/client/connection/src/browser-auth.ts`, `rpc-host.ts`); unary calls are `POST /api/<namespace>/<method>` with `{ type: 'client-request', rpcId, method, payload: { args } }`; streams share one socket at `/api/remote.mux` (`{ type: 'open', streamId, endpoint, payload }` in, `item`/`end`/`error` out — `packages/api/gateway/src/stream-protocol.ts`). Only `session/list` and `session/follow` are used; the `$events` stream is deliberately NEVER opened, because its waterfall frames (approval/request, user-questions/request) stall host settlement process-wide unless the subscriber answers each one.

## Boot Flow

`boot()` in `main.ts:461-547`, in order:

1. Single-instance lock; `second-instance` restores/focuses the window.
2. Profile resolution: `dev = !app.isPackaged`; dev mirrors `~/.dsh` → `userData/dsh-test-home` (config only, `node_modules` skipped); packaged omits `DSH_HOME` → real `~/.dsh`.
3. Profile bootstrap: `ensureProfileInitialized(effectiveHome, 'web', dshCliPath(), process.execPath)`. A machine that never ran dsh has no `profiles/web`, and provisioning can only enrich a profile that exists — so the CLI is asked to initialize it first (a boot-free `--profile web --dump-config`, the same shipped-template initialization its own first boot performs). The app never writes that manifest: a scaffolded one would shadow the shipped bundle list. Fail-soft — a bootstrap that fails logs and the boot continues exactly as it did before the pass existed.
4. Built-ins: `ensureBuiltinPlugins(effectiveHome, 'web', dshCliPath(), process.execPath, vendorPluginsRoot(), bundledSrcRoot())`.
5. Skills: `skillsDir()` resolves `packages/uniterra-skills/src/skills` under the source root (dev AND packaged — the embedded source tree), passed as `DSH_BUNDLED_SKILL_DIR` (rank-600 provider) if it exists.
6. Agent-preset compat: `ensureAgentPresetCompatibility(effectiveHome, bundledSrcRoot())` — the legacy `code` settings default only, since session headers migrate natively in dsh (see `src/preset-compat.ts`); the workflow-capsule slot (`ensureWorkflowCapsules(effectiveHome, skillsDir())`) shares it — the bundled `review` capsule is provisioned into `$DSH_HOME/workflows` (byte-idempotent) and the retired `implement` / `simplify` capsules (`RETIRED_WORKFLOW_CAPSULES`) are removed there on every boot.
7. Update check scheduled after `UNITERRA_UPDATE_DELAY_MS` (default 5000 ms).
8. `startDsh({ profile: 'web', dshBundledSkillDir })`, then the notification surface against the SAME profile dir: `installApplicationMenu(profileDir)` + `startTurnObserver(handle.url, profileDir)` (the observer returns synchronously and runs detached — see below).
9. Crash-restart wiring: on runtime death with window alive, stop the turn observer, then backoff restart `min(1000·2^restarts, 15_000)`.
10. `createWindow(handle.url)` — `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
11. Lifecycle: `window-all-closed` → quit (even macOS — no dock daemon); `before-quit` → `stopDsh` + `app.exit(0)`; `activate` → recreate window from `runtime.url`.

Boot failure surfacing: any `boot()` rejection (initial boot or crash-restart) is routed through `reportStartupFailure` — it appends the error (including the dsh child's captured stderr, which `startDsh` folds into the message) to `userData/startup-error.log`, and on the FIRST boot also raises a native `dialog.showErrorBox` before `app.quit()`. Restart failures log only (no dialog spam).

## Update Check

`initUpdateChecker()` (`main.ts:278-291`) schedules `runUniterraStartupUpdateCheck()`: probes GitHub latest release + npm `latest` dist-tag in parallel, probes `uniterra --version` (3 s timeout). Verdicts via `@uniterra-solutions/uniterra-updater` (see [uniterra-updater.md](uniterra-updater.md)); the prompt response is mapped to the action by `resolveUpdateAction` and the spawn spec by `updateInvocation`. Overridable: `UNITERRA_UPDATE_API_BASE`, `UNITERRA_UPDATE_NPM_URL`, `UNITERRA_UPDATE_COMMAND`, `UNITERRA_UPDATE_RELEASES_PAGE`, `UNITERRA_UPDATE_DELAY_MS`. Prompt: Update Now / Later / Skip This Version (persisted to `userData/uniterra-update-state.json`). Update Now spawns the updater **detached before `app.quit()`** (so it survives the shutdown) — the default invocation is `npx --yes @uniterra-solutions/uniterra@latest update`, which always runs the LATEST updater and refreshes the CLI, rebuilds + reinstalls the app, and relaunches it when done: the relaunch IS the restart. (npm shims are `.cmd` on Windows — `shell: true` resolves them via PATHEXT.)

## Turn-Completion Notifications

A finished turn raises ONE native OS notification, so a user who stepped away from a long agent run is told it is done. The feature replaced the retired `dsh-notifier` plugin (a standalone notifier whose surface overlapped dsh-better-sidebar's Tasks page) with something the shell owns end to end — no plugin, no profile bundle row.

| Piece        | Where                      | Behaviour                                                                                                                                                                                                                    |
| ------------ | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preference   | `~/.dsh/.uniterra.json`    | `notifications.turnComplete`, **default ON** (a missing file, or a file without the key, means on). The app menu's Notifications checkbox is the only writer; the write is additive and an illegible file is never rewritten |
| Menu         | `installApplicationMenu()` | Application menu, Notifications submenu — the checkbox mirrors the file at boot and persists on click; a failed write logs and never takes the app down                                                                      |
| Decision     | `src/notifications.ts`     | Pure: one `turn/end` frame → `{ title: <session title>`, body: <reason mapped to status> }`, or `undefined` for every other frame                                                                                            |
| Replay guard | `createTurnDeduper()`      | One (session, turn) notifies at most once, across reconnects — a follow stream replays its opening window by design                                                                                                          |
| Observer     | `src/turn-observer.ts`     | Follows user-facing sessions only (`subagent` origins are skipped), consults the toggle PER EVENT, never rejects, never stops at the first failure                                                                           |
| Transport    | `src/dsh-observer.ts`      | Detached: exchanges the readiness token for the `dsh-auth-<hash>` cookie, polls `session/list` every 5 s for sessions created after boot, follows each over `/api/remote.mux`                                                |

**Fail-soft by construction.** No cookie, a refused socket, a malformed frame or a dead runtime all degrade to "no notifications" and are logged — nothing throws out of the caller and nothing blocks boot. The observer is started after `startDsh` and stopped on `handle.exited` and on quit.

**Why not the `$events` stream.** It carries waterfall frames (`approval/request`, `user-questions/request`) that stall host settlement process-wide unless the subscriber answers each one. `session/list` + `session/follow` give the turn lifecycle without ever owing the host an answer.

Live verification: `scripts/verify-turn-notification/run.sh` boots the bundled dsh in a throwaway `DSH_HOME` and drives the real transport against it (auth + list + follow); the pure halves are pinned by `test/turn-notification-pbt.test.mjs`, `test/turn-notification-preference-pbt.test.mjs`, `test/turn-observer-pbt.test.mjs` and `test/turn-observer-transport.test.mjs`.

## Patterns & Gotchas

- `ELECTRON_RUN_AS_NODE=1` on both the dsh child spawn and `dsh plugin add` — the Electron binary runs as plain Node. `NO_COLOR=1` keeps stdout parse-friendly.
- Readiness is parsed per COMPLETE stdout line: `awaitReadiness` only inspects text up to a `\n`, and resolves the first line carrying `http://127.0.0.1:<port>`. Newline termination — not a lookahead — is what keeps both the port digits and the `?token=` tail intact across arbitrary chunk boundaries; regression-locked in `builtin-pbt.test.mjs`. dsh 0.1.5-rc.2 prints the line byte-identically to 0.1.2-rc.1 (`dsh web: <url>` plus an optional ` (LAN: <url>)`), from the web app rather than the launcher.
- `startDsh` passes `--no-open`: dsh hands its readiness URL to the operating system's default browser unless told otherwise, and the shell IS this app's browser (the `BrowserWindow` loads that same URL). URL printing and the browser handoff are independent switches, so the readiness line is unaffected. Verified against the built CLI on 0.1.5-rc.2 with a `PATH`-shadowed `open`: without the flag the OS opener receives `http://127.0.0.1:<port>/?token=<token>`, with it no handoff happens and the readiness line still arrives.
- `startDsh` fails fast when the child dies before readiness: it races the readiness wait against the child's `exit` and rethrows the captured stderr immediately. Measured on 0.1.5-rc.2 with the port already in use — the rejection names `dsh exited with code 1 before reporting readiness` after ~7.4 s (the child's own startup), where the readiness timeout alone held for the full 60 s and reported a generic failure. The losing wait is cancelled with the race (its timer and its stdout listener), so a dead child leaves nothing pending — without that cancellation the 60 s readiness window kept the process alive after the failure: the spawn-contract suite in `test/dsh-process.test.mjs` held for 60.1 s before the cancellation and finishes in 2.1 s with it.
- `ensureBuiltinPlugins` returns early when the profile dir doesn't exist — it enriches an existing profile, never scaffolds one. Boot step 3 (`ensureProfileInitialized`) is what makes the profile exist on a first launch, and it always goes through the CLI: the app never writes a profile manifest. Measured on a throwaway home with no `profiles/` at all (dsh 0.1.5-rc.2, boot replayed through the compiled desktop modules): without the bootstrap pass the first boot ended on the bare shipped template — `bundles = ["@deepseek-ai/dsh-base","@deepseek-ai/dsh-web-app"]`, `hasAllBuiltins` false, no `@dsh-external/workflow` layer in the composed tree, so `run_workflow` was unavailable; with it, boot #1 ends with all 12 bundle rows (`hasAllBuiltins` true), the review capsule in `$DSH_HOME/workflows` and the `@dsh-external/workflow` layer composed.
- Vendored plugins are copied, not `dsh plugin add`-ed (peers only exist in the dsh source workspace); workspace built-ins ship pre-built with no pnpm install — a missing `packages/uniterra-provider/lib/` breaks boot (0.6.1 regression). Optional plugins (the Deep Whale skin) follow the same copy path but only when the profile's `.uniterra.json` toggle enables them — `reconcileOptionalPlugins` enforces the toggle before the provisioning gate (fresh installs never get the skin; existing row-bearing profiles migrate to enabled and are preserved; disabling removes the row and the copy; an illegible toggle file is never destructive and never overwritten).
- Staleness is content identity in `copyEntryStale()` — the SAME rule for vendored AND workspace copies: the source-vs-installed `package.json` `version` OR the content fingerprint of the implementation files shared by both sides, so a locally patched copy that changed under the SAME version still propagates. A bundle list can never tell staleness: a fixed distribution ships under the same package name. Optional entries are exempt — their freshness is owned by `reconcileOptionalPlugins`, so a disabled optional (no copy at all) never forces a re-provision on every boot.
- `profile.ts` was removed: it was legacy (its `PROFILE_PLUGINS` list and `profileManifest()` disagreed with `builtin.ts`'s live registry and were never imported at runtime); its test file went with it.
- `scripts/prepare-runtime.mjs` was removed: orphaned since the 0.5.0 `vendor/dsh-runtime` model (no script, CI step, or boot path references it; the output dir no longer exists).
- No code signing: macOS sets `hardenedRuntime: false` + `identity: null` (no quarantine needed); Windows sets `signAndEditExecutable: false` — Uniterra ships unsigned, and skipping the sign step also stops electron-builder from downloading/extracting its `winCodeSign` tool, whose 7z archive contains macOS symlinks that 7-Zip cannot create on Windows without Developer Mode / administrator privileges (electron-builder#8149).
- On Windows the CLI probe and Update Now spawn npm shims (`uniterra` / `npx` as `.cmd`) with `shell: process.platform === 'win32'` — execFile cannot launch `.cmd` shims directly (`spawn ENOENT`); cmd.exe resolves them via PATHEXT (args are fixed, no quoting risk).

## Decisions

| Decision                                                                                     | Rationale                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Thin Electron window over the bundled dsh CLI; no reimplementation                           | Uniterra IS the dsh desktop surface — user's normal dsh config, no app-owned home                                                                                                                                                                                       |
| Dev mirrors `~/.dsh` to a test home; packaged uses the real one                              | Dev never touches the user's real config                                                                                                                                                                                                                                |
| Renderer fully sandboxed (`contextIsolation`, no nodeIntegration, `sandbox`)                 | dsh Web UI is a plain SPA on loopback                                                                                                                                                                                                                                   |
| Copy vendored plugins instead of pnpm-installing                                             | Their peers aren't on npm                                                                                                                                                                                                                                               |
| Version-drift re-provisioning                                                                | Same package name can ship a fixed distribution (the whale-skin swap)                                                                                                                                                                                                   |
| Keep the `code` user-preset shim on 0.1.5 (session headers migrate natively)                 | Measured: 0.1.5-rc.2 rewrites `agentPreset: "code"` in every v0/v1/v2 header and `agent-preset/selected` event, but reads the settings row `agent-presets.default: code` verbatim, so `resolve()` throws until the row exists; removal condition in the Files row above |
| Whole source tree embedded in the app resources (`Contents/Resources/src` / `resources/src`) | Packaged app resolves everything from the embedded source — `process.resourcesPath` is platform-neutral                                                                                                                                                                 |
| electron-builder never reinstalls node_modules                                               | The extracted tree already has them; reinstalling trips the root husky prepare                                                                                                                                                                                          |
| Quit on `window-all-closed` even on macOS                                                    | No dock-resident daemon — the runtime lives only while the window is open                                                                                                                                                                                               |
| Bounded exponential backoff on runtime crash (cap 15 s)                                      | Self-heal without a hot loop                                                                                                                                                                                                                                            |
| Startup failures written to `userData/startup-error.log` + first-boot dialog                 | A broken install must never fail as a silent 60 s hang — the child's stderr (the real `ERR_MODULE_NOT_FOUND`) surfaces to the user                                                                                                                                      |
| Turn notifications owned by the shell, not a plugin                                          | Replaces the retired `dsh-notifier`; the decision is pure and testable, and `session/list` + `session/follow` never owe the host an answer (the `$events` waterfall would stall settlement process-wide)                                                                |
| Notification preference defaults ON, stored in the shared `.uniterra.json`                   | Works out of the box; sharing the file with the optional-plugin toggle keeps the writes additive and an illegible user file intact                                                                                                                                      |     |

## How to Update

- Boot order / paths change → update Boot Flow and Path Resolution tables.
- New built-in added → see [vendor-plugins.md](vendor-plugins.md#how-to-update).
- Update-check wiring changes → update the Update Check section and [uniterra-updater.md](uniterra-updater.md).
- Turn-notification change → update the section above and re-run `scripts/verify-turn-notification/run.sh` (the transport seams are live facts, not conventions).

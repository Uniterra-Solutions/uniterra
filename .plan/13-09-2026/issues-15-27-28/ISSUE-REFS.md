### 內文關鍵段落（逐字引用）

> ## 1. Overview
>
> Currently, the Uniterra AI agent lacks visual feedback during the version update sequence. After a user authorizes a version update, the process executes entirely in the background without status indicators, progress tracking, or a final completion notification.

> ## 2. Problem Statement
>
> - **Opaque Execution:** Users cannot determine the current state of the system (e.g., whether the update is initializing, downloading, installing, or stalled).
> - **User Experience (UX) Degradation:** Given that `npm` installations and dependency updates for the DeepSeek harness can be time-consuming, the absence of system feedback causes ambiguity.
> - **Risk of Premature Termination:** Users may forcefully terminate the agent under the assumption that the application has frozen, which carries the risk of corrupting the installation or leaving dependencies in an inconsistent state.

> ### 3.1. Phase 1: Initialization
>
> - Display an immediate system message upon user consent acknowledging the start of the process.
> - _Example:_ `[INFO] Initializing update process... Please do not close the application.`

> ### 3.2. Phase 2: Active Progress Tracking
>
> - Provide continuous visual feedback during the download and `npm` installation phases to indicate that background processes are active.

> ### 3.3. Phase 3: Completion Notification
>
> - Output a definitive success or failure message upon conclusion of the update process.
> - Include instructions for subsequent user actions if necessary.
> - _Example:_ `[SUCCESS] Update to version X.X.X completed successfully. Please restart the agent to apply changes.`

> ## 4. Technical Considerations
>
> Given the project's reliance on a Node.js/`npm` environment, the following lightweight CLI solutions are recommended for the implementation:
>
> - **`ora`**: To deploy terminal spinners for indeterminate wait times (e.g., resolving packages).
> - **`cli-progress`**: To render terminal progress bars if exact installation metrics or download bytes are measurable.
> - _(Note: If Uniterra utilizes a Graphical User Interface (GUI), these CLI concepts should be adapted into standard frontend loading bars or spinners.)_

> ## 5. Expected Outcome
>
> Enhanced system transparency, improved user confidence during maintenance operations, and a reduction in user-induced installation failures.

### 本檔如何處理這段內文

- 第 4 節建議的 `ora` / `cli-progress` **不得成為本計劃的依賴**（本工作單禁止新增 dependency）。要求改寫成「以 repo 既有手段可達成的可觀察行為」，見 `REQ-15-1`～`REQ-15-3`。
- 第 3 節的三個階段被拆成 `REQ-15-6`（初始化告知／進行中回饋／完成與失敗通知），並由 `REQ-15-1`／`REQ-15-4` 提供機器可讀的底層事件。
- 第 2 節「Opaque Execution」對應的機械原因是子程序輸出被整段緩衝（已查證事實 V-08），對應 `REQ-15-1` 與 `REQ-15-6`。

**對應 REQ**：`REQ-15-1`、`REQ-15-2`、`REQ-15-3`、`REQ-15-4`、`REQ-15-5`、`REQ-15-6`、`REQ-15-7`、`REQ-15-8`。

> - 在 `builtin.ts` 以 `kind: 'vendor'` 宣告（package 名、dir 依實際 vendored 結果）。
> - 安裝目標為 skill root（`~/.dsh/skills` 或 profile 對應路徑），模型 skill tool 能讀取。

> ## 驗收標準（Acceptance Criteria）
>
> 1. `QQ-M/dsh-skill-market` 已 vendored lock pin 進 `vendor/dsh-plugins/`，`VENDOR.md` 記錄 divergence + pending-upstream 註記。
> 2. `builtin.ts` 以 `kind: 'vendor'` 宣告 skill market built-in，`copyBuiltinsStale()` / provisioning 迴圈能正確 provision。
> 3. `pnpm --filter @uniterra-solutions/uniterra-desktop test`（built-ins/readiness PBT）全綠；新增或沿用之 provisioning/readiness 測試涵蓋此 built-in。

> ## 約束條件（Constraints）
>
> - 走既有 vendored built-in 機制，不另建新 provisioning 路徑。
> - 鎖 pin 出處，不直接沿用 npm latest；在 `VENDOR.md` 記 local divergence（若有）。

### 內文關鍵段落（逐字引用）

> ## 背景 / 問題
>
> `uniterra update` 執行完後，會同時開啟 desktop UI（Electron視窗）與 web UI（瀏覽器分頁），而不是僅後者。

> ## 現況
>
> - update 的 launch/app 環節（`packages/uniterra-cli/src/cli.ts` `openApp()`、`launchTarget()`）負責啟動 Electron desktop app。
> - desktop app 啟動後（`packages/uniterra-desktop/src/main.ts` `boot()`、`startDsh()`）會拉下 dsh web UI，並在 Electron `BrowserWindow` 內載入該 URL。
> - 目前異常：update 後除 Electron 視窗外，還額外打開了一個瀏覽器分頁/獨立 web UI，造成雙開。

> ## 預期
>
> - `uniterra update` 完成後**僅**啟動單一 Electron desktop 視窗（desktop UI），不再自動開啟瀏覽器分頁/獨立 web UI。

> ## 契約（Contract）
>
> - 對 `uniterra update`（含 desktop 端 "Update Now" 觸發的更新）的每一步：**只存在一個** launch 路徑，且該路徑指向 Electron desktop app。
> - dsh runtime 子程序不得在 desktop 之外另開瀏覽器分頁。

> ## 驗收標準（Acceptance Criteria）
>
> 1. 執行 `uniterra update` 後，僅一個 Electron desktop 視窗被啟動；無額外瀏覽器分頁/獨立 web UI 被開啟。
> 2. dsh runtime 啟動參數不含會觸發 auto-open browser 的旗標（或在 desktop 情境將其抑制）。
> 3. 既有 install-logic / desktop 測試全綠；新增或沿用一項驗證「update 後僅單一 surface 被啟動」的測試。

> ## 約束條件（Constraints）
>
> - 只在 launch/app-boot 路徑修正雙開，不更動其它更新流程。
> - 不影響 `--no-open`（使用者可不自動開啟）行為。
> - 維持 desktop app 作為 dsh web UI 的唯一載入介面（`BrowserWindow`）。

### 本檔如何處理這段內文

- 驗收標準 2 在 HEAD 上**已經部分成立**：`startDsh()` 的 argv 已含 `--no-open`（V-09），且已有一條 spawn 斷言（V-10）。因此本計劃**不宣稱 bug 已修好，也不宣稱 bug 仍存在**；「雙開從哪來」寫成未確認事項 OQ-28-1，並指定確認方式（V-12、V-13 提供候選）。
- 驗收標準 1 的行為定義寫成 `REQ-28-4`，驗收標準 2 寫成 `REQ-28-3`，契約「只存在一個 launch 路徑」寫成 `REQ-28-1`。
- 約束條件「不影響 `--no-open`」寫成 `REQ-28-2`；「不更動其它更新流程」寫成 `REQ-28-6`。

**對應 REQ**：`REQ-28-1`、`REQ-28-2`、`REQ-28-3`、`REQ-28-4`、`REQ-28-5`、`REQ-28-6`。

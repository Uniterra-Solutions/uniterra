# ACCEPTANCE — property-based acceptance strategy for issues #15 / #27 / #28

**證據標準。** 本計劃所有測試皆為 **property-based test**（repo 既有的 `node:test` + `fast-check@^4.9.0` 疊層）；example-based 斷言**只允許**作為「已確認反例」的 deterministic regression **追加**，不得取代、不得放寬它所對應的那條 property。任何「跑一次看輸出對不對」的斷言都不是驗收證據。

**每個套件的實跑指令**（只從這張表抄，不得自創；這些 script 今天真的存在）：

| 套件（`--filter`） | 實跑指令                                                  | 收檔 glob                                                                                      | fast-check 疊層                |
| ------------------ | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------ |
| `uniterra-cli`     | `pnpm --filter @uniterra-solutions/uniterra test`         | `test/**/*.test.mts`（測試前先 `tsc -p tsconfig.test.json`，其 `include` 為 `["src","test"]`） | `^4.9.0`（既有 devDependency） |
| `uniterra-desktop` | `pnpm --filter @uniterra-solutions/uniterra-desktop test` | `test/*.test.mjs`（**頂層、不含子目錄**、無 tsc 前置）                                         | `^4.9.0`（既有 devDependency） |
| `uniterra-updater` | `pnpm --filter @uniterra-solutions/uniterra-updater test` | `test/**/*.test.mts`                                                                           | `^4.9.0`（既有 devDependency） |

- **不要**把 fast-check 屬性測試放進 `packages/uniterra-skills` 或 `packages/uniterra-provider`：那兩個套件**沒有** fast-check（`ISSUE-REFS.md` V-35／V-36），要用就得先問「新增 dependency」。因此本計劃的所有新測試落點都在上表三個套件內。
- 本計劃**不使用** `uniterra-updater` 的落點：它今天的測試檔只有 `packages/uniterra-updater/test/decision.test.mts`，而 #15／#27／#28 的契約邊界都落在 CLI 或 desktop 兩側。
- **新檔**一律明示；既有檔案的擴充一律寫「既有檔案」並註明追加在哪個既有測試家族之下。
- live harness（`scripts/verify-*`）只能作**輔助證據**，不得取代 property；本計劃引用的三支今天都存在：`scripts/verify-turn-notification/run.sh`、`scripts/verify-cli-container/run.sh`、`scripts/verify-dsh-shortcuts-smoke/run.sh`（`ISSUE-REFS.md` V-39）。

## Property 目錄

每一段寫：名稱（沿用 repo 的「大寫不變式 + 冒號 + 一句話」風格）、被鎖的不變式、生成域、為何這個生成域足以證偽、退化輸入。

### #15

**`PROGRESS-SCHEMA: encoding is decoded back to the same event with an exact key set`**
被鎖的不變式：編碼／解碼互為反函式，且事件的鍵集合是封閉的（不得多、不得少）。生成域：任意 `(event, stage, status, seq, message)` 組合，其中 `message` 涵蓋空字串、100 KB 字串、含換行、含 `@@uniterra`、含非 BMP 字元。為何足以證偽：鍵集合封閉性一旦被打破（多一個欄位或漏一個欄位），反函式就不再成立，而任意生成的組合都能把它逼出來。退化輸入：`message: ''`、只有 `run-start` 的單元素序列、seq 為 0 的單筆事件、恰好等於前綴本身的 message。

**`PROGRESS-SEQ: seq starts at 0 and increments by exactly one per run`**
被鎖的不變式：同 run 內 seq 是 0..n-1 的排列且相鄰差恰為 1。生成域：任意 stage 序列（含空、含重複、含亂序的 stage 名稱清單）。為何足以證偽：任何跳號、重號、或跨 run 汙染都會在某一條生成序列上出現。退化輸入：空序列（0 個事件）、單一事件、全部 stage 相同。

**`PROGRESS-PARTITION: filtering the sentinel restores the event stream exactly`**
被鎖的不變式：混流是可逆的——過濾前綴後剩下的事件行序列等於原事件序列，剩下的人類行序列不含任何事件行。生成域：任意長度的（人類行, 事件）交錯序列，人類行由任意可列印字串生成。為何足以證偽：只要有任何一個人類行「看起來像」事件，或事件前綴被生成器寫壞，等價性就破。退化輸入：零個人類行、零個事件、人類行恰好是空行、人類行是 `@@uniterra` 但沒有尾隨空白。

**`PROGRESS-NOANSI: no escape byte is ever emitted, TTY or not`**
被鎖的不變式：輸出位元組集合不含 `0x1b`，且四個（TTY × `NO_COLOR`）組合下位元組完全相同。生成域：任意事件序列 × 四個環境組合。為何足以證偽：任何「偵測 TTY 才輸出顏色/進度條」的實作都會在其中一個組合下改變位元組。退化輸入：單一事件、空序列、`message` 本身含 `0x1b`（必須被轉義或拒絕，不得原樣輸出）。

**`PROGRESS-SINK: the durable record is line-for-line the event stream`／`PROGRESS-SINK: unset or dry-run leaves zero file side effects`**
被鎖的不變式：有指定檔案且非 dry-run ⇒ 檔案內容逐行等於 stdout 的事件行，且 append 不產生重複 `(run, seq)`；未設或 dry-run ⇒ 目標目錄不存在或為空。生成域：任意事件序列 × 任意路徑（既有目錄／深層不存在目錄／含空白與非 ASCII 的檔名）× 三種模式（設定、未設、dry-run）。為何足以證偽：任何「先寫檔再修正」「dry-run 也建目錄」「重跑時重寫整份」的實作都會被某一組輸入抓到。退化輸入：零事件（檔案應存在但為空，或依規格不建立——以實作選定的語意鎖進 property）、路徑指向唯讀目錄（必須 fail-soft）。

**`PROGRESS-PHASES: every executed stage brackets itself and the run ends once`**
被鎖的不變式：每個實際執行的 stage 恰有一次開始行與一次結束行且順序正確；run 尾恰有一個總結行；失敗時總結行指名 stage。生成域：任意非空 stage 子序列。為何足以證偽：把某個 stage 的開始行省略、或把總結行寫兩次，都會在單元素或三元素序列上失敗。退化輸入：只有一個 stage、三個 stage 全在、`launch-app` 缺席。

**`PROGRESS-TOTAL: the reducer is total over arbitrary bytes`**
被鎖的不變式：解碼與歸約對任何輸入都不拋出；無法解析的行被忽略而不是中斷。生成域：任意 `Uint8Array`（含非 UTF-8、截斷 JSON、超大行、只有換行、外來前綴、NUL byte）。為何足以證偽：任何 `JSON.parse` 未包在 try 內、或對缺欄位直接取屬性的實作，都會被某個位元組序列打到。退化輸入：空檔案、單一換行、合法事件被截掉最後一個字元。

**`PROGRESS-MONO: replayed out-of-order events never regress the state`／`PROGRESS-IDEMPOTENT: a duplicated (run, seq) is a no-op`**
被鎖的不變式：已確認完成的階段不退回；重複的 `(run, seq)` 不改變狀態；任意前綴的狀態是完整序列狀態的較早狀態。生成域：任意事件序列的任意排列與任意 `(run, seq)` 重複注入。為何足以證偽：任何「以最後一個事件覆蓋狀態」的實作都會在亂序輸入下退回。退化輸入：兩個事件交換順序、同一事件連餵兩次、空序列。

**`PROGRESS-RENDER-ONCE: a terminal state renders exactly once`**
被鎖的不變式：只有在存在未消費的終態時才回傳 payload；同一終態第二次詢問必為 undefined。生成域：任意行序列（含空檔、只有 `run-start`、`run-end/ok`、`run-end/failed`、兩個 run 相接、損壞行夾雜）。為何足以證偽：把「有檔案」當成「要顯示」的實作會在只有 `run-start` 的輸入上失敗。退化輸入：空檔案、單一損壞行、兩個 run 相接。

## 紅燈基準（Red baseline）

施工時每一條 property 的**紅燈都必須是行為性的斷言失敗**（`AssertionError`／property 回報的 counterexample），**不是** import／編譯錯誤。做法：

1. 先以**真實簽名**加入 stub（C1～C6 的純函式，回傳值刻意錯，例如回傳 `[]`／`undefined`），讓測試檔能載入、能執行。
2. 跑該套件指令，確認紅燈的形狀是「`PROGRESS-SEQ` 在 seq = 0,1,1,3 上失敗」這種**指名反例**，而不是 `TypeError: x is not a function`、`ERR_MODULE_NOT_FOUND`、或是 `tsc` 的型別錯誤。

## 反例 → deterministic regression

規則（與 `AGENTS.md`／`docs/conventions.md` 的既有慣例一致）：

1. property 抓到反例後，**先確認**那是最小輸入（縮小到不可再縮），把該具體輸入與「不變式要求的確切結果」寫成一則 **deterministic regression** 測試。
2. regression 測試**命名以測試目的為準**（它鎖住哪個保證），**不得帶 finding id／issue 編號**。
3. regression 是**追加**：被鎖的 property 必須原樣保留，**不得刪除、改名、放寬或跳過**。regression 通過不代表 property 可以退場——兩者永久並存。
4. 同一條 property 若再次抓到**不同**的反例，就再追加一則 regression；不得把多個反例合併成一則無關的斷言。
5. regression 放在與其 property **同一個測試檔**（或該套件的既有 regression 檔，例如 desktop 的 `preset-compat-regressions.test.mjs` 這種既有命名法）；本計劃不新增 regression 檔。

本計劃中**已可預期**的 regression（施工時若真的抓到，就照上面規則落地）：`PROGRESS-SEQ` 的跳號最小輸入、`SURFACE-UNIQUE` 的 `dryRun: true` 反例、`PROVISION-HEAL-IDEMPOTENT` 的「第二次 ensure 又重寫 manifest」反例、`NO-AUTHOR-PATH` 的 `/root/.dsh/skills` 命中。

## 替代證據

只能用在**確實鎖不住**的部分；每一條都寫「誰、在哪個平台、跑什麼、看什麼、什麼叫通過」。

- **A-15-1（知覺：desktop 真的把結果顯示給使用者）** 人：開發者。平台：macOS。跑什麼：在**拋棄式** `DSH_HOME` + 一個假 updater（`UNITERRA_UPDATE_COMMAND` 指向一支會寫入合法 NDJSON 記錄的腳本）下啟動 desktop，讓它讀到 `run-end/ok` 與 `run-end/failed` 兩種記錄。看什麼：兩種記錄各出現恰好一次原生結果，成功訊息說明明確、失敗訊息指名 stage；重啟 app 後**不再**顯示。什麼叫通過：三次啟動中，前兩次各顯示一次、第三次不顯示，且 `startup-error.log` 沒有新增。**這是 `REQ-15-5`／`REQ-15-6` 的 GUI 一半。**
- **A-15-2（知覺：人在終端看到進展）** 人：開發者。平台：macOS（終端）與非 TTY（管線）。跑什麼：`uniterra update --dry-run` 與一次 `--no-open` 的真實 update（若允許）。看什麼：初始化告知在階段開始前出現、每個階段一進一出、結尾恰一個總結行；`uniterra update | cat` 時事件仍完整。什麼叫通過：人眼對照 `REQ-15-6` 的四個要素全中。
